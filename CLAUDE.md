# Fish War

## 0. Commands

Package manager is **pnpm** (via corepack: `corepack enable pnpm`). Root scripts
fan out through Turborepo; all commands below are verified.

* Install: `pnpm install`
* Dev (all): `pnpm dev` — or per app: `pnpm --filter @fishwar/web dev`, `pnpm --filter @fishwar/game-server dev`
* Build: `pnpm build` (only `@fishwar/web` has a build; the server runs from source via `tsx`)
* Typecheck: `pnpm typecheck` (strict TS across all packages)
* Lint: `pnpm lint` (single root flat ESLint config)
* Test (all): `pnpm test`
* Test (one package): `pnpm --filter @fishwar/game-core test`
* Test (one file / name): `pnpm --filter @fishwar/game-core test -- <file-or-pattern>`
* Run server standalone: `pnpm --filter @fishwar/game-server start` (WebSocket on `PORT`, default 8080)

### Workspace layout

* `apps/web` — Next.js (App Router) + React 19. Rendering/UI only.
* `apps/game-server` — Node + `ws` WebSocket server; runs TypeScript via `tsx` (no build step yet).
* `packages/game-types` — shared engine-agnostic types (e.g. `Role`, `ROLES`).
* `packages/game-core` — pure gameplay functions (Vitest-tested); depends only on `game-types`.
* `packages/config` — shared `tsconfig.base.json` and `eslint.base.mjs`.

### Conventions that aren't obvious from the tree

* **Internal packages export TypeScript source** (`"exports": "./src/index.ts"`), not built
  `dist`. Consumers transpile them: web via `transpilePackages` in `next.config.mjs`,
  server via `tsx`, tests via Vitest. So there is no build-ordering step for libs — but any
  new internal package must be added to web's `transpilePackages` list.
* **Lint runs from the root only** (`eslint .`), not per-package via Turbo. The shared base is
  in `packages/config/eslint.base.mjs`; React rules are layered on `apps/web` in the root
  `eslint.config.mjs`.
* **Per-package tooling is explicit**: pnpm does not hoist root binaries into package scripts,
  so `typescript` (and `vitest` in game-core) are declared as devDeps in each package that
  invokes them.
* `next-env.d.ts` is generated by Next and gitignored — do not edit or rely on committing it.

## 1. Project

Fish War is a 1v1 asymmetric multiplayer fishing battle game.

Two roles:

* Fish
* Fisherman

Fish tries to escape.
Fisherman tries to capture the fish.

The game starts with a fishing simulation but becomes an arcade/comedic battle.

---

## 2. MVP

The MVP contains only:

* 1 map
* 1 Fish
* 1 Fisherman
* 1 Rod
* 1 Reel
* 1 Fishing Line
* 1 Fishing Net
* 1 Water Gun
* 1v1 multiplayer

Do NOT implement:

* Ranked system
* Shop
* Battle pass
* Cosmetics
* Multiple maps
* Guild
* Tournament
* Trading
* Voice chat
* Mobile version
* Open world
* Complex economy

---

## 3. Core Gameplay

### Fish

Fish can:

* Move
* Swim
* Sprint
* Dash
* Escape
* Dive
* Attack with water gun
* Attempt to break fishing line
* Become exhausted

### Fisherman

Fisherman can:

* Move
* Dodge
* Cast
* Control rod
* Adjust drag
* Reel
* Use fishing net

The fisherman cannot directly attack the fish.

---

## 4. Game Rules

Fish wins if:

* Fishing line breaks
* Fish escapes
* Fisherman is knocked out
* Match timer expires and Fish survives

Fisherman wins if:

* Fish becomes exhausted
* Fisherman successfully captures Fish with the net

---

## 5. Architecture

Use a monorepo.

Applications:

* apps/web
* apps/game-server

Shared packages:

* packages/game-core
* packages/game-types
* packages/config

Keep these concerns separated:

* Rendering
* Gameplay
* Physics
* Networking
* UI
* State management

Do not put gameplay logic directly inside React components.

## 7. Gameplay Architecture

Gameplay rules should preferably live in:

packages/game-core

Shared types should live in:

packages/game-types

Rendering-specific logic belongs in:

apps/web

Server-authoritative gameplay belongs in:

apps/game-server

---

## 8. Multiplayer

The server is authoritative.

The client must NOT be trusted for:

* Damage
* Stamina
* Line tension
* Capture
* Win/lose
* Cooldowns
* Server-side movement validation
* Match state

Client sends player intent/input.

Server calculates the authoritative result.

Target:

* Client: 60 FPS
* Server: 20-30 ticks/sec

---

## 9. Physics

Do not build a fully realistic rope simulation for MVP.

Use a stable gameplay-oriented line model.

The fishing line should support:

* Maximum length
* Tension
* Fish pulling force
* Rod force
* Reel
* Drag
* Line breaking

Physics calculations must be independent from React rendering.

---

## 10. Development Rules

Before implementing a non-trivial feature:

1. Inspect the existing code.
2. Identify affected files.
3. Explain the implementation approach.
4. Implement the smallest working version.
5. Run typecheck.
6. Run lint.
7. Run tests.
8. Fix errors.
9. Summarize changes.

Do not rewrite unrelated code.

Do not add dependencies without explaining why.

Do not implement future features unless explicitly requested.

Do not create unnecessary abstractions.

Prefer simple, testable systems.

---

## 11. Code Rules

Use TypeScript strict mode.

Prefer:

* Small functions
* Small classes
* Explicit types
* Pure gameplay functions where possible
* Composition over inheritance
* Shared types instead of duplicated types

Avoid:

* `any`
* Global mutable state
* Giant React components
* Giant game classes
* Circular dependencies
* Duplicated game rules
* Magic numbers

---

## 12. Dependency Rules

Before adding a dependency:

1. Check whether the existing stack can solve the problem.
2. Explain why the dependency is needed.
3. Explain the impact on architecture.
4. Only then add it.

Do not add libraries simply for convenience.

---

## 13. Task Scope

Only implement the requested task.

Do not automatically implement:

* Future roadmap items
* Extra UI
* Extra gameplay
* Extra systems
* Refactors unrelated to the task

If the requested implementation requires architectural changes, explain them before making them.

---

## 14. Definition of Done

A task is complete only when:

* Feature is implemented
* TypeScript passes
* Lint passes
* Tests pass when applicable
* No console errors
* No obvious runtime errors
* No unused imports
* No unrelated files changed
* Feature can be manually tested
* Documentation is updated if architecture changed

---

## 15. Current Development Strategy

Build in this order:

1. Project initialization
2. Basic 3D scene
3. Fish movement
4. Fisherman movement
5. Fishing rod
6. Fishing line
7. Line tension
8. Drag and reel
9. Fish stamina
10. Fish dash
11. Water gun
12. Fisherman dodge
13. Fishing net
14. Capture system
15. Match state
16. Multiplayer
17. Server authority
18. Prediction/interpolation
19. UI

Do not skip directly to complex multiplayer before the offline gameplay loop is playable.

---

## 16. Important Principle

Make the game playable before making it beautiful.

Make the gameplay fun before adding content.

Make the offline core stable before adding multiplayer complexity.
